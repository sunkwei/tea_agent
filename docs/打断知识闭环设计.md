> **版本**：v1.0（已实现）
> **状态**：✅ 已实现（M1-M4 全部落地，2026-08-03）
> **关联模块**：`session/tool_loop_runner.py`、`onlinesession.py`、`basesession.py`、`store/_interruptions.py`、`agent_background.py`、`prompt_manager.py`、`config.py`、`server/route_handlers.py`
> **一句话**：把「用户打断」从被动标记升级为**结构化否定信号**，形成「打断 → 纠正 → 学习 → 减少同类打断」的自进化闭环。

## 1. 背景与问题

### 1.1 现状（基于代码事实）

tea_agent 的打断是**协作式**的，而非强杀：

| 环节 | 代码位置 | 行为 |
|---|---|---|
| 触发 | `basesession.py:799` `interrupt()` | 仅设置 `self.interrupted = True` 标志 |
| 检测 | `session/tool_loop_runner.py:432` | 工具循环检查点检测标志，**优雅退出** |
| 收尾 | `tool_loop_runner.py:432-437` | 已生成内容保留，追加 `[已打断]` 作为最终回复，`add_assistant_message` + `collect_interruption_round` |
| 入库 | `agent.py:403-411` → `_post_chat_pipeline` | chat_stream 返回后**统一保存**整轮（user_msg + ai_msg + rounds） |

因此：**正常打断不丢信息**，`[已打断]` 标记会随对话历史持久化，并在后续对话中作为历史消息可见。

### 1.2 核心洞察

> **打断 = 隐式负面反馈（implicit negative feedback）。**

用户主动打断，说明 AI 当前的思考过程 / 输出方向**不符合人类判断**。这在机器学习中属于偏好学习（preference learning）的信号：**被否定的轨迹** 与 **用户随后的行为**（纠正 / 换话题 / 沉默）构成可学习的偏好对。

### 1.3 现有不足

1. **无语义**：`[已打断]` 仅是文本标记，模型不知道「哪一步、哪个方向」不符合预期；
2. **无锚点**：未记录打断发生时正在执行什么工具、生成到哪一段、第几轮循环；
3. **浪费纠正信号**：打断后用户通常马上输入纠正指令（"不是这样"、"重新做"），这个最关键的反饋未被结构化利用；
4. **无长期沉淀**：不统计「哪类任务 / 工具 / 输出格式频繁被打断」，无法驱动进化；
5. **无方向弃用感知**：用户打断后切换话题 = 方向被弃用，当前机制完全无法感知，模型可能在后续会话「旧事重提」。

## 2. 目标与非目标

### 2.1 目标

- **G1（即时）**：打断时记录结构化锚点（在做什么工具、第几轮、已生成内容），作为上下文注入后续会话；
- **G2（短期）**：根据用户下一条消息自动分类打断信号（纠正 / 换话题 / 沉默），分别注入不同提示；
- **G3（长期）**：周期性地将打断模式沉淀为偏好记忆，并反馈到 prompt / 技能进化，降低同类打断率；
- **G4（可观测）**：打断事件可查询、可统计、可回溯。

### 2.2 非目标（v0.1 明确不做）

- 不做打断的**即时终止**改造（流式循环内检查点属另一议题）；
- 不做对用户行为的**强假设**（如自动改写用户消息）；
- 不修改对话历史的存储 schema 破坏性迁移（仅新增表 / 字段，向后兼容）。

## 3. 信号分类

打断后的用户行为构成完整的否定信号谱系：

| 信号 | 触发条件 | 语义 | 强度 | 后续处理 |
|---|---|---|---|---|
| `corrected` | 下一条消息与打断轨迹**语义相似**（≥阈值） | 方向修正：当前方向错了，给出新方向 | 强 | 注入「该方向被否定，请按新指令调整」 |
| `abandoned` | 下一条消息与打断轨迹**语义漂移**（<阈值） | 方向弃用：当前方向不值得继续 | 中强 | 注入「上一方向已被用户弃用（用户转而处理 Y）」+ 短期记忆 |
| `silent` | 无下一条消息 / 长时间沉默 / 关窗 | 方向放弃：被弃且无新方向 | 弱 | 仅写入短期记忆，不主动注入 |

**分类判定依赖下一次对话开始时**：`corrected` vs `abandoned` 只有看到用户下一条消息才能区分。

## 4. 总体架构

三层知识管道，各层职责与生命周期不同：

```
┌──────────────────────────────────────────────────────────────────┐
│  用户层  │ 打断发生 → 下一条消息进入 → 后续对话 → 周期统计          │
└──────────┴────────────────────────────────────────────────────────┘
          │
┌─────────▼──────────────────────────────────────────────────────────┐
│  L1 即时上下文（打断锚点记录）                                      │
│  · 位置：tool_loop_runner.py 打断检查点                             │
│  · 内容：InterruptionEvent 结构化记录 → 注入 system 消息            │
│  · 生命周期：单次对话内生效                                         │
├─────────────────────────────────────────────────────────────────────┤
│  L2 短期记忆（打断-纠正学习对）                                     │
│  · 位置：onlinesession.py chat_stream 入口（检测上一轮打断）         │
│  · 内容：{partial_reply, followup_user_msg, classification}         │
│  · 生命周期：会话期间 / session memory                             │
├─────────────────────────────────────────────────────────────────────┤
│  L3 长期沉淀（模式统计与进化）                                      │
│  · 位置：后台自进化线程 / reflection / memory auto_extract          │
│  · 内容：打断率统计 → 偏好记忆 → prompt_evolve 反馈                 │
│  · 生命周期：跨会话持久                                               │
└─────────────────────────────────────────────────────────────────────┘
```

## 5. 数据模型

### 5.1 打断事件（InterruptionEvent）

内存对象 + 持久化到 `chat_history.db` 新表 `interruption_events`：

```json
{
  "id": "uuid",
  "topic_id": "会话主题ID",
  "conversation_id": "被打断那一轮的对话记录ID（可为空，若入库前）",
  "timestamp": "ISO-8601 时间戳",
  "iteration": 3,                    // 工具循环第几轮被打断
  "tool_name": "toolkit_exec",       // 打断时正在执行的工具（若有）
  "tool_args_summary": "前120字符摘要",
  "partial_reply": "已生成的文本内容（截断至 2000 字符）",
  "phase": "tool_loop | text_stream",  // 打断发生在工具循环还是文本生成
  "status": "pending | classified",    // 待分类 / 已分类
  "classification": null | "corrected" | "abandoned" | "silent",
  "similarity": null | 0.72,           // 语义相似度（corrected/abandoned 判定依据）
  "followup_user_msg": "用户下一条消息（截断至 500 字符）",
  "followup_ts": null | "ISO-8601"
}
```

SQL 建表（向后兼容，新增表不破坏现有 schema）：

```sql
CREATE TABLE IF NOT EXISTS interruption_events (
  id TEXT PRIMARY KEY,
  topic_id TEXT,
  conversation_id TEXT,
  timestamp TEXT,
  iteration INTEGER,
  tool_name TEXT,
  tool_args_summary TEXT,
  partial_reply TEXT,
  phase TEXT,
  status TEXT DEFAULT 'pending',
  classification TEXT,
  similarity REAL,
  followup_user_msg TEXT,
  followup_ts TEXT
);
CREATE INDEX IF NOT EXISTS idx_interrupt_topic ON interruption_events(topic_id);
CREATE INDEX IF NOT EXISTS idx_interrupt_status ON interruption_events(status);
```

### 5.2 会话内锚点（内存）

`SessionContext` 增加一个属性，保存「最近一次打断」的锚点，供下一次 `chat_stream` 检测：

```python
# SessionContext / OnlineToolSession
self._last_interruption: InterruptionEvent | None = None
```

### 5.3 长期沉淀（偏好记忆）

沿用现有 `memory` 体系，新增分类 `category="preference"`、标签 `tag="interruption"`：

```json
{
  "content": "用户在处理『X类任务』时曾打断并改为『Y方式』（发生2次）",
  "category": "preference",
```

## 6. 核心流程（时序）

### 6.1 打断发生 → 锚点记录

```
用户点击打断 / 快捷键
  → basesession.interrupt() 设置标志
  → tool_loop_runner 检查点（432行）检测 interrupted
  → 组装 final_msg = partial + "[已打断]"
  → ① 记录 InterruptionEvent（iteration/tool/partial_reply/phase）
  → ② add_assistant_message(final_msg)        # 上下文可见
  → ③ collect_interruption_round(final_msg)   # 入库 rounds
  → ④ session._last_interruption = event      # 内存锚点
  → 返回 interrupted=True
  → chat_stream 返回 → _post_chat_pipeline 统一入库
```

### 6.2 下一条消息 → 分类 → 注入

```
用户输入新消息 M
  → chat_stream 入口（onlinesession.py 约1734行）
  → 检测 self._last_interruption 非空？
      ├─ 是：取 embedding(M) 与 embedding(partial_reply) 相似度
      │      ├─ ≥0.6 → corrected
      │      ├─ <0.6 → abandoned
      │      └─ 无 M（超时/关窗）→ silent（不在此处处理，后台补标）
      ├─ 注入 system 消息（见 7.3 注入模板）
      └─ 更新 event.status/classification/similarity/followup
  → 正常处理 M
```

### 6.3 周期沉淀

```
后台自进化线程（每小时）
  → 查询 interruption_events where status='classified'
  → 按 tool_name / 任务关键词 聚合打断率
  → 打断率超阈值（如 ≥2次同类）→ 写入 preference 记忆
  → 可选：反馈 prompt_evolve / skill 调整建议
```

## 7. 详细设计

### 7.1 L1：打断锚点记录（`session/tool_loop_runner.py`）

在现有打断检查点（约 432 行）扩展，用独立方法组装事件：

```python
def _record_interruption(session, iteration, current_tool, partial_reply):
    """记录打断锚点。返回 InterruptionEvent（内存+DB）。"""
    ev = InterruptionEvent(
        topic_id=session.topic_id,
        timestamp=now_iso(),
        iteration=iteration,
        tool_name=current_tool.name if current_tool else None,
        tool_args_summary=truncate(current_tool.arguments, 120) if current_tool else None,
        partial_reply=truncate(partial_reply, 2000),
        phase="tool_loop",
        status="pending",
    )
    session._last_interruption = ev
    # 异步写 DB（不阻塞返回路径）
    thread_pool.submit(db.insert_interruption_event, ev)
    return ev
```

设计要点：
- **非阻塞**：DB 写入放线程池，避免打断返回路径被 IO 拖慢；
- **幂等**：同一打断只记录一次（检查点单次触发）；
- **tool_loop 与 text_stream 两处**：文本生成阶段的打断（若后续加入流式检查点）走同一记录函数，`phase` 区分。

### 7.2 L2：分类判定（`onlinesession.py` chat_stream 入口）

复用已有 `embedding_util.EmbeddingEngine`（项目已用于语义搜索），新增轻量判定函数：

```python
SIMILARITY_THRESHOLD = 0.6  # 可配置

def classify_interruption(event, user_msg) -> str:
    """corrected / abandoned / silent"""
    if not user_msg:
        return "silent"
    emb_u = embedding_engine.embed(user_msg)
    emb_p = embedding_engine.embed(event.partial_reply)
    sim = cosine_similarity(emb_u, emb_p)
    event.similarity = sim
    return "corrected" if sim >= SIMILARITY_THRESHOLD else "abandoned"
```

位置：`chat_stream` 开头（约 1734 行，解析 `msg` 之后、构建 messages 之前）注入。

### 7.3 注入模板（system 消息）

| 分类 | 注入模板 |
|---|---|
| `corrected` | `[系统] 上一轮生成已被用户打断（当时正在执行 {tool_name}，第 {iteration} 轮）。用户接下来的指令为：「{followup}」。请将这次打断视为对之前方向/方式的否定，按用户最新指令重新规划，不要继续被打断前的思路。` |
| `abandoned` | `[系统] 上一轮方向已被用户弃用（用户转向了新话题）。后续回复请聚焦当前话题，不要主动回到上一轮被打断的内容。` |
| `silent` | 不注入（仅沉淀记忆，见 7.4） |

模板常量放 `prompt_manager.py`，支持后续 prompt 进化统一管理。

### 7.4 L3：长期沉淀（后台线程）

在现有后台自进化线程（`agent_background.py`，每小时轮询）追加一个步骤 `analyze_interruptions()`：

1. 查询近 7 天 `interruption_events`（`status='classified'`）；
2. 按 `tool_name` 与任务关键词聚合，计算打断率 `interrupt_count / total_sessions`；
3. 阈值：同一 `tool_name` 打断 ≥ 2 次 或 同类任务 ≥ 2 次 → 写入 preference 记忆（§5.3）；
4. 生成建议文本（如"用户在该类任务中偏好直接回答而非长工具链"），供 `prompt_evolve` 评估，**不自动改 prompt**（仅产出建议，由人工/反思确认）。

## 9. 边界情况与权衡

| # | 场景 | 处理策略 |
|---|---|---|
| 1 | **连续多次打断** | 每次打断独立记录；注入时仅取最近一次（`_last_interruption` 覆盖），避免上下文膨胀 |
| 2 | **打断后长时间不说话** | 超时（如 10 分钟）无下一条消息 → 后台补标 `silent` |
| 3 | **打断发生在文本流式生成中** | v0.1 不处理（流式循环无检查点）；`phase='text_stream'` 字段预留，待流式检查点落地后填充 |
| 4 | **语义相似度误判** | 阈值 0.6 可配置；仅注入提示不改写用户消息，误判成本低（多一条 system 提示） |
| 5 | **embedding 服务不可用** | 降级：退化为「有下一条消息 → corrected；无 → silent」，跳过 abandoned 判定（保守策略，宁可不注入也不误注入） |
| 6 | **打断轮次尚未入库（进程被强杀）** | 事件表单独插入（7.1 非阻塞），入库窗口更短；强杀窗口内事件丢失可接受（与现有对话历史一致） |
| 7 | **token 预算** | 注入模板 ≤ 300 token；仅当 `_last_interruption` 存在且为 corrected/abandoned 时注入一次 |
| 8 | **隐私** | `partial_reply` / `followup_user_msg` 截断存储；事件表默认保留，支持清理任务 |

## 11. 风险与缓解

| 风险 | 等级 | 缓解 |
|---|---|---|
| 打断返回路径被 DB 写阻塞（打断本身变慢） | 中 | 线程池异步写（7.1）；写失败仅记日志不抛异常 |
| 语义误分类导致错误引导模型 | 中 | 阈值可配置；embedding 不可用时保守降级（宁缺毋滥）；只注入不改写 |
| 上下文 token 膨胀 | 低 | 单次注入 ≤300 token；仅最近一次打断生效 |
| 事件表无限增长 | 低 | 保留策略（默认 30 天清理，可配置） |
| 与现有 `_post_chat_pipeline` 时序冲突（conversation_id 未生成） | 低 | 事件表 `conversation_id` 允许 NULL，入库后由 `_post_chat_pipeline` 补写（`UPDATE ... SET conversation_id=?`） |
| 后台分析打扰用户 | 低 | 分析只读事件表 + 写记忆，不触碰对话历史 |

### 12.2 集成验证（手动剧本）

1. **corrected 剧本**：让 AI 执行长工具链任务 → 中途打断 → 输入"不是这样，直接告诉我结论" → 断言：AI 不再继续工具链，直接给结论；
2. **abandoned 剧本**：AI 在讨论 A 方案时打断 → 输入完全不相关的新问题 → 断言：AI 不再提 A 方案；
3. **持久化**：打断后重启应用 → `interruption_events` 表可查询到记录；
4. **回归**：全量 `pytest` 通过，打断路径耗时 < 200ms（不因本功能变慢）。

### 12.3 效果指标（长期观测）

- 打断率 = 打断次数 / 对话轮数：期望 M4 后 30 天环比下降；
- `corrected` 占比高说明模型方向感差（调 prompt）；`abandoned` 占比高说明模型话痨/跑题（调输出风格）。
