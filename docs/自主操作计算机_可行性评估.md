# tea_agent 自主操作计算机 — 可行性评估

> 评估日期：2026-09-20 · 评估环境：Windows 10 (10.0.19045) AMD64 / 2560×1440 @200% DPI / Python 3.14.7
> 方法：全部结论基于**本机实测**，非纸面推演。工具口径按 `tk.py` 实测：56 模块 / 60 注册 / 58 可见。

---

## 0. 结论速览

| 能力 | 现状 | 结论 |
|------|------|------|
| ① 鼠标键盘 | `toolkit_input` 已存在且**实测可用** | ✅ 底座已具备，但有 4 个硬缺口 |
| ② 进程/应用感知 | 无专用工具，但底层通路**全部实测打通** | ⚠️ 可直接建，工作量小 |
| ③ GUI 界面理解 | `toolkit_screenshot` + `toolkit_vision_analyze` 可用；UIA/OCR **实测打通** | ✅ 三层方案均可行，首选 UIA |
| ④ 安全护栏 | **完全缺失** | 🔴 最高优先级，先于功能落地 |

**一句话**：技术可行性没有障碍，三个问题都有确定性答案；**真正的风险不在"能不能做"，而在"做完之后 Agent 能做什么"** —— 当前 `toolkit_input` 在实际风险分级中被评为"常规工具"（`classify_risk` 返回 `None`），零审计、零审批，而它等价于"以用户身份对这台电脑为所欲为"。

## 2. 问题①：如何操作鼠标、键盘

### 2.1 现状可用性（实测）

```
toolkit_input(action='screen_size') → {"width": 2560, "height": 1440}
toolkit_input(action='position')    → {"x": 969, "y": 373, "screen": "2560x1440"}
```

底层是 `pyautogui 0.9.54`，能力覆盖 move / click / double_click / right_click / drag / scroll / type / press / hotkey，加上 `FailSafe`（鼠标甩到左上角 (0,0) 即中止）。

### 2.2 🔴 硬缺口 1：DPI 坐标陷阱（本机已复现）

本机是 **2560×1440 物理 / 1280×720 逻辑，缩放 200%**，这是最容易出错的场景。实测结论：

| 场景 | `GetSystemMetrics` | 截图尺寸 | pyautogui 坐标 | 能否对齐 |
|------|-------------------|---------|---------------|---------|
| 先 `import pyautogui` | 2560×1440 | 2560×1440 | 2560×1440 | ✅ 对齐 |
| 先 `import mss` | **1280×720** | 2560×1440 | 2560×1440 | ⚠️ 逻辑/物理混用 |

根因：`pyautogui/_pyautogui_win.py` 在导入时执行 `ctypes.windll.user32.SetProcessDPIAware()`。而 **DPI 感知是进程级、只能设置一次**：

```
SetProcessDpiAwareness(2) → 0        # 成功
SetProcessDpiAwareness(0) → -2147024891 (0x80070005 拒绝访问)  # 二次修改失败
```

> **推论**：agent 进程里"截图"和"点击"看到的是不是同一个坐标系，**取决于模块导入顺序**——这在长驻服务里是隐性的、随机的。
>
> **对策**：在进程启动最早期（早于任何截图/输入库导入）固定 DPI 策略为 **per-monitor v2**，并在工具初始化时**自检断言** `截图尺寸 == 输入坐标系尺寸`，不一致直接报错拒绝对话，而不是"点歪了但没人知道"。

### 2.3 🔴 硬缺口 2：没有中文输入能力（已实测确认）

```
pyautogui.KEYBOARD_KEYS → 194 个键
非 ASCII 键 → []           '中' in keys → False
```

`toolkit_input(action='type', text='中文')` **无法工作** —— `typewrite` 逐字符查键盘映射表，非 ASCII 直接失败。中文/表情/任意 Unicode 必须走**剪贴板注入**（写剪贴板 → `Ctrl+V`）。项目已有 `toolkit_clipboard`，属可复用的现成拼图。

### 2.4 🔴 硬缺口 3：副作用不可逆 + 与用户争抢桌面

- 每一次 click 都是**不可回滚的真实世界动作**：可能删了文件、发了消息、付了款。项目里其他写操作用 `.bak` / git 快照兜底，鼠标点击**没有等价物**。
- Agent 是以"和用户同一个桌面会话"的身份运行的（实测 `WindowStation=WinSta0`、`Desktop=Default`、`Session=Console`）。**用户正在用电脑时 Agent 一动鼠标，双方就在抢同一个光标**。这不是理论风险 —— 本次评估期间 Agent 自己截图拍到的就是用户正在使用的 Chrome 和终端窗口。
- `FailSafe` 是唯一的刹车，但它在无人值守/多屏/远程桌面下不可靠（鼠标本来就可能在左上角）。

**对策**：引入「桌面占用锁」——Agent 操作前声明占用、操作中用户动键鼠即让位、操作后释放；高风险动作前插入截图确认点。

### 2.5 🟡 已知边界：权限与窗口消息

被 `UIPI`（User Interface Privilege Isolation）保护的高完整性进程（UAC 提升后的窗口），低完整性进程的合成输入会被**静默丢弃**。涉及管理员权限的场景无解，只能提示用户手动操作 —— 这与项目既有原则一致（`_CRITICAL_TOOLS` 注释里明确写了"Agent 不允许获取管理员权限"）。

## 3. 问题②：如何知道哪些应用在执行、装了哪些应用

此问题**技术难度最低、收益最直接**，且所有通路均已在本次评估中实测跑通。

### 3.1 「正在执行」的两个层次

**A. 进程层（有什么在跑）** — `psutil 7.2.2`，实测枚举 **203 个进程**，字段 `pid / name / exe / rss`：

```
Weixin.exe 474MB | chrome.exe 367MB | explorer.exe 288MB | wps.exe 204MB ...
```

**B. 窗口层（有什么可见、在哪、前台是谁）** — **纯 ctypes，零第三方依赖**，实测枚举到 5 个可见顶层窗口：

```
Chrome_WidgetWin_1  "…bilibili - Google Chrome"  pid=16516  rect=[-7,-7,1286,686]
CASCADIA_HOSTING_WINDOW_CLASS "Python venv_work" pid=14436  rect=[18,49,1108,575]
Progman            "Program Manager"             pid=5512   rect=[0,0,1280,720]
```

可拿到：`hwnd / 标题 / 窗口类名 / pid / 精确矩形 / 是否最小化`，外加 `GetForegroundWindow()` 判断前台应用。

> **建议**：窗口层优先用 **ctypes** 而非 `pywin32`。本次实测 `win32gui` 在 agent 的**子进程**解释器里 `ModuleNotFoundError`，而 ctypes 是永远可用的（`user32.dll` 系统自带）。少一个依赖 = 少一个静默失效点。

### 3.2 「装了哪些应用」的四条通路（均已实测）

| 通路 | 实测数量 | 适用场景 |
|------|---------|---------|
| 注册表 `Uninstall` 键 | **143** 条 | 传统安装的软件（含版本号） |
| 开始菜单 `.lnk` | **123** 个 | 人类视角的"我能启动什么"，含中文名（豆包、WPS） |
| 注册表 `App Paths` | **29** 条 | `start <exe名>` 可直达（msedge.exe、7zFM.exe） |
| `Get-AppxPackage` | **76** 个 UWP | Store 应用，含 `PackageFamilyName` |

**启动方式**同样是四条，全部可用：
- 传统程序 → `os.startfile(exe)` 或 `subprocess.Popen(exe)`
- 开始菜单项 → `os.startfile(<.lnk路径>)`
- UWP/Store 应用 → `explorer.exe shell:AppsFolder\<PackageFamilyName>!App`

> ⚠️ 注意：三条通路存在**同名不同实**（如 `msedge.exe` 在 App Paths 与 `.lnk` 中指向不同版本），工具需要做去重与优先级裁决，否则会出现"打开了但开的是另一个版本"。

## 4. 问题③：GUI 应用如何理解界面数据

这是核心难点。**单一方案都不够，需要三层降级**。三层均已实测验证，且**坐标空间一致（均为 2560 物理像素）**，可互相锚定。

### L1 结构层：UI Automation（首选）

通过 PowerShell + 系统自带 `UIAutomationClient` 实测，**零 pip 安装**即可读取 Chrome 窗口的完整元素树：

```
WINDOW: …bilibili - Google Chrome
buttons=19
  BTN 2286,0   90x80  | 最小化
  BTN 2468,0   92x80  | 关闭
  BTN 0,92     80x68  | 返回
edits=1
  EDIT 316,102  value=bilibili.com/video/BV1Gwe363EB8/...
```

**能拿到**：元素名 / 控件类型 / **精确矩形坐标** / **控件的实际值**（地址栏内容）/ 可调用的模式（Invoke、Value、Selection、Toggle）。

**优势**：确定性高、token 极省（比截图便宜几个数量级）、可直接得到"点哪里"，无需视觉模型猜坐标。**应作为默认路径。**

**局限（必须提前知晓）**：
- Chrome 的**网页内容区**在 UIA 树里是不可见的（只暴露窗口 chrome/工具栏），要读 DOM 得走 CDP —— 项目已有 `toolkit_js_fetch`(Playwright) 可覆盖这条。
- Java(Swing)、WPF 自绘、DirectX/游戏画面 → UIA 树为空或极浅，必须降级到 L2/L3。
- 当前实现方式（PowerShell 子进程）每次约 1–2 秒启动开销，且中文输出有编码坑。**进程内方案需要 `comtypes` + `UIAutomationCore.dll`**，环境里 `comtypes` 当前未安装 —— 这是要补的依赖。

### L2 文本层：系统 OCR（零安装，已实测）

**WinRT `Windows.Media.Ocr`**，实测结果：

```
BITMAP 2560x1440
ENGINE zh-Hans-CN  maxDim=10000
OCR_MS 383  lines=49  WORDS_total=588
  WORD0='小'  Rect(X=1096, Y=31, W=24, H=21)
```

- **零 pip 安装**（系统自带），支持 **zh-Hans-CN / en-US**
- **全屏 2560×1440 仅 ~400ms**，输出**逐词精确坐标**（物理像素，与 UIA/截图同空间）
- 适用：Canvas 绘图、游戏、图片型界面、UIA 无输出的应用

> 踩坑记录：`TryCreateFromLanguage([Language]::new("zh-Hans-CN"))` 在 PowerShell 里会因 WinRT 类型封送失败，需改用 `TryCreateFromUserProfileLanguages()`（实测有效）。另外 PS 封送 `Windows.Foundation.Rect` 时需先取出再访问字段。

### L3 语义层：视觉模型（已可用，克制使用）

`toolkit_vision_analyze` 实测返回：

> "主要窗口是一个浏览器中打开的本地 Tea Agent GUI 界面（127.0.0.1:8282），左侧为会话列表，中间展示了一条关于项目内技术评估的思考过程与工具调用记录。"

**用于**：整体布局理解、歧义消解、验证"这一步做完了吗"。**代价**：一次全屏视觉推理的成本 ≈ 数百次 UIA 查询，应作为**兜底与校验**，而非主路径。

### 三层协同

```
        观察意图
           │
    ┌──────▼──────┐  有 UIA 树？
    │ L1 UIA 结构 │──是──► 元素名+坐标+值  ──► 直接点击，成本最低
    └──────┬──────┘
           │否（Canvas/游戏/自绘/网页正文）
    ┌──────▼──────┐
    │ L2 OCR 文本 │─────► 文字+逐词坐标     ──► 定位点击
    └──────┬──────┘
           │上下文不足 / 需理解语义
    ┌──────▼──────┐
    │ L3 VLM 视觉 │─────► 自然语言理解      ──► 消歧 / 校验
    └─────────────┘
      三层坐标同为 2560 物理像素，可交叉验证
```

## 5. 🔴 安全评估：当前最大的漏洞

### 5.1 实测发现：`toolkit_input` 处于监管真空

读取 `tool_approval.py` 的 `classify_risk()` 逐条比对：

| 工具 | 分级 | 理由 |
|------|------|------|
| `toolkit_exec` | **high** | "执行系统命令（可变更文件系统/环境）" |
| `toolkit_self_evolve` | **critical** | "可修改自身代码/提升权限" |
| `toolkit_file`(write) | medium | "写入文件" |
| **`toolkit_input`** | **None** | **"常规工具"** ← 不在 `_HIGH_TOOLS` / `_MEDIUM_TOOLS` / `_CRITICAL_TOOLS` 任何清单中 |

**它既不被审计（`make_pre_hook` 在 `level is None` 时直接 `return True`，连审计日志都不写），也不被审批拦住（enforce 模式对它是透明的）。**

而它的实际危害上界是：**以用户身份执行任意 GUI 操作** —— 点"发送"把消息发给任何人、点"删除"清空回收站、在浏览器里下单、改系统设置。这比 `toolkit_exec` 的能力边界**更大**，因为它绕过了命令行的一切审计痕迹。

### 5.2 建议的最小护栏（按优先级）

1. **纳入分级**：把 `toolkit_input` / 未来的 GUI 工具划入 **high**，`classify_risk` 里可按"目标窗口"细分（操作浏览器 vs 操作系统设置 vs 操作 IM 应用）。
2. **桌面占用锁**：Agent 操作期间独占，检测到用户输入即暂停并归还控制权。
3. **动作前快照**：每个破坏性动作（点击按钮）前自动截图存证，作为审计附件（复用 `audit_log` 的 hash 链）。
4. **会话级熔断**：单次会话内的 GUI 动作次数上限，超限强制转人工确认。
5. **默认关闭**：`TEA_COMPUTER_USE=0` 为默认值，需显式开启 —— 参照 `TEA_TOOL_SHIELD` 的既有模式。

## 6. 落地建议（分阶段）

| 阶段 | 内容 | 依赖 | 风险 |
|------|------|------|------|
| **P0** | 安全护栏：分级 + 审批 + 审计 + 占用锁 + 开关 | 无 | 无（纯加固） |
| **P1** | `toolkit_window`：窗口/进程/应用枚举与启动（ctypes+psutil 为主） | 无（零新依赖） | 低 |
| **P2** | `toolkit_ui_tree`：UIA 结构化读取（进程内 comtypes，PS 子进程兜底） | `comtypes` | 中（依赖/编码坑） |
| **P3** | `toolkit_ocr`：WinRT OCR 零安装文本层 | 无（系统自带） | 低 |
| **P4** | 观察-动作闭环编排（步数上限 + 每步校验 + 失败重试） | P0–P3 | **中高** |

**几点实现约束（源自实测）**：
- **禁止用 `python` 子进程做 GUI 操作**：实测 agent 进程内 `pyautogui` 可导入，但 PATH 上的 `python` 是 base 解释器，**没有 pyautogui** —— 子进程方案会以"静默 No Module"的方式失败。
- DPI 策略必须在进程最早启动时固定并**断言自检**。
- 工具列表顺序影响前缀缓存（项目既有约束），新增 4 个 GUI 工具需确认排序确定性。

## 7. 总体判断

**技术侧：可行，且比预期简单。** 三个问题分别在本次评估中被实测验证：手（pyautogui 可用）、应用感知（ctypes+psutil+注册表，零新依赖）、界面理解（UIA/OCR/VLM 三层均跑通）。真正需要补的依赖只有一个 `comtypes`。

**风险侧：当前不可直接放开。** `toolkit_input` 事实上已经给了 Agent 一个**无审计、无审批、不可回滚、且会与用户争抢桌面**的任意操作通道。在补上分级与审批之前，不建议再往上叠加"看界面→自动点击"的闭环能力 —— 那会把一个"手"升级成一个"无人监督的操作员"。

**建议路径：先加固（P0），再扩能力（P1→P4）。**
